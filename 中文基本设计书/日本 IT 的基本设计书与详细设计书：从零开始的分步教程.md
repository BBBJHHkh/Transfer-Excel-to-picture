# 日本 IT 的基本设计书与详细设计书：从零开始的分步教程

**适用对象：** 想学习日本软件开发现场文档写法的初学者。本文用一个小型业务系统贯穿说明，并配套 Excel 练习模板。

## 先记住一句话

> **基本设计（基本設計／外部設計）回答：用户和外部系统能看到什么、系统应该做什么（What）。**
>
> **详细设计（詳細設計／内部設計）回答：程序、数据库和模块怎样实现这些行为（How）。**

这不是“基本设计写得粗、详细设计写得细”这么简单。两者首先是**读者和决策对象不同**。基本设计通常需要让客户、业务人员、项目经理和开发者共同确认；详细设计主要服务于实现人员。

## 一、先了解日本现场的实际情况

日本 IT 项目通常会把设计内容拆成许多 Excel 或 Word 成果物，而不是所有内容都放进一个巨大文件。常见成果物包括：功能一览、画面一览、画面迁移图、画面项目定义、帐票一览、表定义、ER 图、接口定义、消息定义、非功能要求、处理定义、模块设计和测试规格书。

但是，各公司和项目的名称并不完全统一。有的团队把基本设计称为“外部设计”，把详细设计称为“内部设计”；有的团队将两者合并成“系统设计书”；还有的团队在一份设计书中同时管理外部信息和实现信息。**不要把模板当作法律格式。应当先确认项目方的文档标准、评审对象和交付范围。**

| 判断维度 | 基本设计 | 详细设计 |
|---|---|---|
| 日文常见名称 | 基本設計書、外部設計書 | 詳細設計書、内部設計書 |
| 主要读者 | 客户、业务方、PM、架构师、开发者 | 开发者、测试人员、运维人员 |
| 核心问题 | 系统要提供哪些功能，用户如何使用 | 每个功能如何处理、校验、读写数据 |
| 典型内容 | 系统构成、业务流程、功能、画面、帐票、数据概要、非功能要求 | 处理步骤、模块、参数、SQL/伪SQL、更新条件、异常、日志、事务 |
| 完成标准 | 业务方能够确认“系统行为符合要求” | 开发者能够据此实现，测试人员能够据此设计测试 |

日本公开资料中，Nablarch 开发标准提供了格式和样例，并强调只记录实现所需的规格，避免不必要的内部细节；DCR 的设计书说明则列举了领域定义、区分定义、表项定义、画面项目、批处理、消息、权限和接口等典型项目。[1] [2]

## 二、贯穿本教程的练习案例

我们假设要开发一个“商品库存查询／入库登记系统”。范围如下：

| 项目 | 内容 |
|---|---|
| 用户 | 仓库员工、管理员 |
| 主要功能 | 商品查询、商品详情、入库登记 |
| 主要画面 | 商品查询画面、商品详情画面、入库登记画面 |
| 主要数据 | 商品主数据、当前库存、入库履历 |
| 非功能示例 | 查询通常负载下 95% 请求在 2 秒内返回；仓库员工不能维护商品主数据 |
| 明确排除 | 支付、采购订单、供应商系统接口 |

学习时不要一开始就写“数据库字段类型”或“Java 类名”。先从业务目标和用户任务开始，再逐层细化。

## 三、完整写作流程：从需求到详细设计

### 第 1 步：写清楚范围和术语

先建立以下四张小表：系统范围、角色、术语、需求列表。每项需求分配唯一 ID，例如 `REQ-001`。后续功能、画面、处理和测试都引用这个 ID。

推荐句式是：

> **[角色] 在 [前提] 下，可以通过 [操作] 完成 [业务结果]。**

示例：

> 仓库员工登录系统后，可以输入商品编号或商品名称查询当前库存。

不要写成“系统支持强大的库存查询功能”。这种句子无法评审，也无法测试。

### 第 2 步：制作基本设计的功能一览

功能一览是基本设计的骨架。先从业务动作拆分功能，不要从程序类拆分功能。

示例：

| 功能 ID | 功能名 | 输入 | 输出 | 对应需求 |
|---|---|---|---|---|
| F-001 | 商品查询 | 商品编号、商品名称 | 商品列表 | REQ-001 |
| F-002 | 商品详情 | 商品编号 | 商品详情、库存数 | REQ-001 |
| F-003 | 入库登记 | 商品编号、数量、日期 | 登记结果、更新后库存 | REQ-002 |

**检查点：** 每一条需求至少对应一个功能；每个功能都有输入和输出；明确不在范围内的内容也要记录。

### 第 3 步：制作画面一览和画面迁移

先列出画面，再决定画面如何连接。画面 ID 应稳定，例如 `SCR-001`，不要用会频繁改变的中文名称当主键。

示例迁移：

```text
商品查询画面
  ├─ 查询成功 → 刷新商品列表
  ├─ 选择商品 → 商品详情画面
  └─ 查询异常 → 错误消息
商品详情画面
  └─ 点击入库 → 入库登记画面
入库登记画面
  ├─ 保存成功 → 商品详情画面并刷新库存
  └─ 校验失败 → 当前画面显示错误
```

基本设计需要让业务方看懂“点击什么、会到哪里、什么情况下失败”。不需要在这里写 Controller、Service 或 SQL。

### 第 4 步：制作画面项目定义

对每个画面，逐项定义标签、输入框、按钮、列表列和错误显示位置。常见列包括：项目 ID、项目名称、部件类型、输入／输出、必填、数据类型、长度、初始值、格式、校验概要、关联表项。

推荐按以下顺序填写：

1. 先画出用户能理解的画面布局。
2. 给每个输入、输出和按钮分配项目 ID。
3. 写清楚输入／输出方向。
4. 写清楚必填、长度、范围和格式。
5. 写清楚错误发生时显示在哪里。
6. 将项目绑定到数据项或功能 ID。

示例：入库数量是整数、必填、最小值为 1、最大值为 999999。仅写“数值”还不够，因为开发者和测试人员不知道边界。

### 第 5 步：制作数据设计

初学者可以先写“表一览”，再写“表定义”，最后再画 ER 图。表一览回答“系统管理哪些业务对象”；表定义回答“每个对象有哪些数据”。

示例：

| 表 ID | 表名 | 用途 | 主键 | 保存期间 |
|---|---|---|---|---|
| TBL-001 | M_PRODUCT | 商品主数据 | PRODUCT_ID | 长期 |
| TBL-002 | T_STOCK | 当前库存 | PRODUCT_ID | 长期 |
| TBL-003 | T_STOCK_IN | 入库履历 | STOCK_IN_ID | 7 年 |

在表项目中至少确认：主键、外键、必填、NULL 可否、数据类型、长度、默认值、唯一约束、索引和保存期间。注意：基本设计中可以先写业务意义；详细设计中再决定物理类型、索引和锁。

### 第 6 步：补齐非功能要求

非功能要求不能只写“性能良好”“安全性高”。应当写成可以讨论、测量和验收的要求。IPA 的“非功能要求等级”用于避免用户与开发者对可用性、性能、扩展性、运用、保守性和安全性产生理解偏差，并建议先确定重要项目，再补充其他项目。[3]

推荐写法：

| 分类 | 不好的写法 | 可评审的写法 |
|---|---|---|
| 性能 | 查询要快 | 通常负载下 P95 响应时间不超过 2 秒 |
| 可用性 | 系统稳定 | 工作日 08:00–20:00 可用；月度可用率 99.5% |
| 安全 | 做好权限 | 仓库员工不能执行商品主数据维护 |
| 运维 | 有日志 | 错误日志记录错误 ID、时间、用户和概要，但不记录密码 |

### 第 7 步：从基本设计展开详细处理定义

每个功能至少要有一个处理定义。详细设计的重点不是把代码逐行翻译成中文，而是把**实现决策**写清楚。

建议固定使用以下结构：

1. 处理 ID 与处理名称。
2. 入口条件与前置条件。
3. 输入参数及其约束。
4. 正常处理步骤。
5. 输出及返回值。
6. 数据库访问与更新条件。
7. 事务边界和排他方式。
8. 异常处理、重试和回滚。
9. 日志和审计记录。
10. 对应的基本设计 ID 与测试观点评审。

入库登记的示例步骤：

```text
1. 检查用户是否具有入库登记权限。
2. 检查商品编号存在。
3. 检查入库数量为 1～999999 的整数。
4. 以请求 ID 判断是否为重复提交。
5. 开始数据库事务。
6. 向 T_STOCK_IN 插入一条入库履历。
7. 对 T_STOCK 的目标商品加行锁，并将库存增加入库数量。
8. 提交事务。
9. 返回登记 ID 和最新库存。
10. 任一步骤失败时回滚事务，输出 MSG-E-002，并记录错误日志。
```

这个粒度比“调用入库 API”有用得多，因为它明确了顺序、事务、锁、重复提交和失败行为。

### 第 8 步：写 DB 访问、模块和消息定义

DB 访问表需要说明访问类型、表、字段、条件、更新内容和排他方式。复杂 SQL 可以先写“伪 SQL”，让非 SQL 专家也能参与评审；Nablarch 开发标准也采用这种思路。[1]

模块定义需要说明调用方、被调用方、参数、返回值和依赖。消息定义需要同时写日文消息、中文含义、发生条件和用户处理方式。错误消息不要只写“系统错误”，应让用户知道下一步如何处理。

## 四、基本设计和详细设计的评审方法

### 基本设计评审

评审重点是业务正确性和范围完整性。请逐项确认：

- 需求是否都能追踪到功能。
- 每个功能是否都有画面、输入、输出或接口。
- 画面迁移是否覆盖正常和异常路径。
- 所有输入项是否有必填、长度、格式和边界。
- 表和字段是否能支撑功能。
- 角色权限是否明确。
- 非功能要求是否能测量或验收。
- 客户能否不看源代码就理解系统行为。

### 详细设计评审

评审重点是可实现性、一致性和异常完整性。请逐项确认：

- 每个基本设计功能是否都有处理定义。
- 处理顺序是否没有歧义。
- 输入、输出与画面项目或接口项目是否一致。
- DB 更新条件是否可能误更新多行。
- 事务边界、锁和回滚是否明确。
- 重复提交、超时、空数据、权限不足和外部失败是否处理。
- 日志是否足够定位问题且不泄露敏感数据。
- 设计 ID 是否能追踪到测试项目。

## 五、如何使用配套 Excel 模板学习

文件中的工作表按 `00`～`10` 编号。建议按以下方式练习：

1. 先阅读黄色示例行，不要马上删除。
2. 用“商品退货登记”新增一个功能 `F-004`，补写画面、数据和处理。
3. 为 `F-004` 设计一个异常：退货数量大于当前库存。
4. 将异常写进画面校验、详细处理、消息定义和测试观点评审。
5. 再增加一个权限规则：只有管理员可以取消入库登记。
6. 最后检查每个 ID 是否可追踪，是否存在孤立的功能、画面或表。

黄色行是参考答案，浅色空白行是练习区。Excel 中的日文列名可以直接作为日本项目现场的表头，中文列名用于学习理解。

## 六、公开参考资料和使用建议

公开模板可以帮助你熟悉日本现场常见的 Excel 结构，但不建议未经裁剪地把所有工作表都塞进每个项目。小型系统没有批处理、帐票或外部接口时，应明确标记“不适用”或删除对应成果物；大型系统则通常需要增加接口、作业流程、邮件、消息、代码表、权限、运维和测试等设计。

推荐阅读顺序是：先看 Nablarch 的格式与样例，再看 DCR 对各类定义项目的说明，然后用 IPA 的非功能要求资料补齐非功能章节。公开的 Exia 页面还提供了基本设计和详细设计 Excel 压缩包，可用于比较不同模板的章节组织方式。[1] [2] [3] [4]
